# 我们的理解：展厅、展品精细化与技术选择

**Whistlevale 的参考价值，是把作品放进可探索的空间，再让每件作品经得起近看。我们的研究由此从“怎样展示”深入到“怎样刻画”，最后通过真实对照判断 Three.js 与原生 WebGL 2 的分工。**

[在线双图导览](https://yydshly.github.io/0913_codex_project/012-whistlevale/research.html) · [原库完整研究](README.md) · [实际技术对照](renderer-comparison.md) · [原生实现过程](webgl2-study.md)

## 一、展厅和展台各自负责什么

展厅负责整体布局、主题分区、进入与返回、参观顺序，让观众先建立“这里有什么、彼此怎样关联”的印象。展台负责一件作品的主体、尺度、看点、镜头和交互，让观众愿意停下来观察。

| 场景 | 适合采用的表达 | 应配套的信息 |
| :--- | :--- | :--- |
| 多个个人作品、研究成果、收藏 | 主题展厅＋每件作品的独立展台 | 能力摘要、作者与来源、实际体验入口 |
| 旅游目的地或陌生地方介绍 | 地域总览＋车站、街区、景点等地点展品 | 真实介绍、位置与路线资料；微缩场景不代替准确地图 |
| 文化、工业、产品或知识展示 | 整体关系＋可近看、拆解、切换状态的对象 | 重点问题、结构说明、操作结果与适用边界 |

空间入口适合探索和建立印象。精确检索、长篇阅读、路线查询等任务，仍应有清晰的目录、文本和地图入口。

## 二、为什么前面的效果还可以继续精修

已有作品优先解决了场景组织、环境、运动和交互；不同部位的制作精度不均衡。车站实验将精力集中到近景：窗框倒角、屋檐接缝、支撑、连接件、铺地，以及木纹、凹凸和光照响应。

基础版与精细版模型量为 3430 与 19168 个三角形。这个对照的两侧都使用原生 WebGL 2，因此展示的是**制作和算法投入的差异**，不能用于证明某种框架画质更低。多面数本身也不保证更好，重点是有用的结构、正确尺度和适合观察的镜头。

后续精修应围绕核心展品最近的观察距离，联合调整模型、材料、灯光和镜头；远景不必采用与重点近景相同的细节预算。

## 三、Three.js 与 WebGL 2 的关系

```text
使用框架：我们的场景与自定义效果 → Three.js → WebGL 2 → GPU
直接编写：我们的场景与绘制流程 → WebGL 2 → GPU
```

WebGL 2 更底层，意味着直接控制缓冲、着色器、绘制顺序和资源管理。它不是“最精细等级”。Three.js 同样允许精细几何、自定义着色器与后处理；是否接管底层和内容做得多精致是两个独立维度。

## 四、实际对照支持什么结论

我们实现了真正的 Three.js 渲染器，并提供两种配置：内置物理材质、贴图与灯光；接入与原生版相同的程序算法。两侧采用同一精细模型、相机、时间与摄影参数；同算法模式还共享表面和阴影计算。

在站房、木纹砖缝、车漆金属、夜景和景深五个固定看点中，同算法对照的 RGB 平均差为 0.000729—0.002371／255，任一通道差值超过 2 的像素占比均低于 0.04%。主要精细效果得以保留；少量像素仍有较大差异，不能宣称逐像素完全一致。内置配置的差异主要来自算法与风格选择，不能当作 Three.js 的能力上限。

这支持我们继续使用 Three.js，并在需要时自定义具体效果。它没有证明任意高级效果都能无成本实现，也没有提供两条路线的单独运行 FPS、开发工时或长期维护成本排名。完整条件、数据和边界见[实测记录](renderer-comparison.md)。

## 五、下一次怎样选择

| 需求 | 默认选择 | 改变选择的依据 |
| :--- | :--- | :--- |
| 展厅、旅游介绍、交互场景、精细展品 | Three.js | 根据内容与目标设备做样板验证 |
| 特定程序纹理、反光、阴影或摄影风格 | Three.js＋自定义算法 | 现成配置不能准确表达目标时补足该项 |
| 学习底层、制作专用渲染器 | 直接使用 WebGL 2 | 目标本身需要控制绘制流程 |
| 已确认关键流程或性能受框架限制 | 针对瓶颈比较局部原生方案 | 用相同效果和目标设备实测收益，再决定是否扩大改造 |

**我们的当前选择：保留 Three.js，优先精修重点展品；原生 WebGL 2 用于理解、实验和定位底层问题。** 不以“更底层”推断“更精细”，也不因缺少细节而先更换框架。
