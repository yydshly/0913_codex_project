后续进展：已从色块扩展到[实际生成的8处景区素材](scenic-material-integration.md)。下文保留首轮色块实验；当前源图与像素证据见新记录。人工位置观察仍非必需，景观语义真实性仍未自动验证。

2026-09-14。用户明确要求系统自行校验位置，不依赖人工认识城市或填写图片观察坐标。此研究取代[上一版研究](position-generation-research.md)中的默认人工观察流程；首页仍保留最新用户景区图，本轮不修改其景观。

## 自动检查如何获得证据

1. 输入有来源的地点与布局。复用8点同一 GCJ-02 坐标，拒绝混用坐标系；本轮没有实现地图数据源间的自动交叉核实。
2. 注册素材的景区 ID、宽高、RGBA 像素、内容 SHA-256 和本地接地点。哈希包含尺寸，避免只改尺寸重解释同一像素数组。
3. 按合成指令实际绘制像素，同时记录每个稳定主体像素的归属编号。原型把 alpha≥0.5 的最上层素材作为归属。
4. 合成结束后另行扫描最终归属栅格，计算每个景区的可见像素数、包围框、重心、超出区域的像素数。结果来自实际执行过的绘制，而非人工填入或仅回读计划坐标。
5. 对照原计划检查：实际变换接地点、可见主体区域、54条有意义的东西／南北顺序、遗漏与重复、素材编号及哈希、可见比例。
6. 导出前从浏览器实际画布重新读取 RGBA，与检查报告中的输出哈希比较。错位或内容不一致时阻止测试图导出；失败报告仍可保存用于诊断。

输出哈希是原始 RGBA 的哈希，不是编码 PNG 文件的哈希。画布宽高随报告一起绑定。源码核心为 [controlled-compositor.mjs](app/controlled-compositor.mjs)，网页调用同一合成模块；不是仅用测试代码模拟生产判断。

## 位置通过究竟说明什么

可以说明：在这次受控绘制流程中，绑定的素材按给定位置规则合成，其主体可见像素未发生可检测的错位、遮挡、漏画、重复或编号串用。

不能说明：

- 上游坐标本身一定真实；错的数据仍会得到内部一致的结果。
- 素材登记为“钟楼”就一定画的是钟楼；编号和哈希不是语义识别。
- 任意外部整张生成图可以靠此算法自动识别景区。该图没有合成时的可靠像素归属证据。
- 浅透明装饰、多层透明雾气或柔和混色已经完整验证。alpha<0.5的像素参与颜色合成，但不参与主体归属，相关遮挡尚有盲区。
- 当前小色块的重心能直接替代真实建筑接地点。真实素材既要声明接地点，还要确认主体轮廓合理。
- 通过小色块即解决8点中4组密集位置的美术容量，或31处景区能自然排布。

因此：位置自动自检与资料真实性、外观真实性、最终审美分开报告。不要求用户手工检查位置，也不承诺目前实现了全自动语义真实性审核。

## 原型阈值

沿用1400×900布局与原有允许圆形区域；画布内最近邻约束决定区域大小。测试素材为16×16像素，由程序缩放至指定区域内，以验证管线。它不是最终素材推荐尺寸。

可见主体比例低于90%失败；主体有任何像素超出允许区域失败。当前阈值刻意严格，用于故障实验，尚未由真实景观校准。不为通过测试扩大区域或将景区移到错误方位。真实素材若太大，应改布局或尺度，再独立检查关系。

## 验证与复现

在 app/ 运行：

```powershell
npm run research
npm test
npm run build
npm run check
```

research 自动生成五种实验报告。新增6项测试验证正常绘制、实际位置互换、漏画、遮挡、错误编号、重复绘制、边缘裁切、素材篡改及输出像素篡改；全项目29项测试通过。构建及78处静态引用、107个控件与语法检查通过。

浏览器实测正常场景自动显示8/8通过；切换位置互换场景出现26项问题，保存合成测试 PNG 按钮禁用。未将此结果记为真实图片语义识别成功。
